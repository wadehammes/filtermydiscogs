- **Account prefs**: **`User.preferences`** JSON stores **`theme`**, **`squareCorners`**, **`view`**, **`defaultCollectionSidePanel`**, **`persistFilters`**, **`filters`**, **`filterViews`**, **`autoPlayOnQueueAdd`**, **`extendQueueWithSimilarReleases`**, and optional **`analyticsConsent`**. Types in [`userPreferences.types.ts`](../../src/types/userPreferences.types.ts) (`ViewMode` from [`view.types.ts`](../../src/types/view.types.ts)). All authenticated **`PATCH`** calls use [`usePersistUserPreferences`](../../src/hooks/usePersistUserPreferences.hook.ts) + [`userPreferencesPersistQueue.ts`](../../src/utils/userPreferencesPersistQueue.ts)—theme/view/filter UI, saved views, **Remember filter selections**, playback settings, and analytics consent in Settings, and first-login seed from [`useUserPreferencesSync`](../../src/hooks/useUserPreferencesSync.hook.ts). Do not call **`useUpdateUserPreferencesMutation`** directly in app code. **`email`** and **`marketing_emails_opt_in`** are **Postgres columns** on **`User`** (not in **`preferences`** JSON); Settings Account uses **`useUserContactQuery`** + **`useUpdateUserContactMutation`** → **`/api/user/contact`** ([`user-contact.server.ts`](../../src/lib/user-contact.server.ts)), separate from the preferences queue. The queue **debounces filters-only patches** (~400ms) and **flushes immediately** for any other preference field (theme, view, toggles, saved views, analytics consent, playback settings); merged patches flush together when a non-filter field arrives. When adding a new preference key, route it through the same queue—do not extend a manual allowlist. Sync hydrates server prefs into theme context, Jotai atoms, and local analytics consent after login. Shared validation: [`view.types.ts`](../../src/types/view.types.ts), [`storedTheme.ts`](../../src/utils/storedTheme.ts), [`filters.types.ts`](../../src/types/filters.types.ts) + [`filtersStorage.ts`](../../src/utils/filtersStorage.ts), [`filterViews.ts`](../../src/utils/filterViews.ts) (`parseFilterViews`, `isValidFilterViewsPatch`), [`sortValues.ts`](../../src/constants/sortValues.ts); storage keys in [`storageKeys.ts`](../../src/constants/storageKeys.ts) (`ANALYTICS_CONSENT_STORAGE_KEY` for local consent).
- **User row**: OAuth callback and token-reuse login upsert a **`User`** row via [`recordDiscogsLogin`](../../src/lib/user.server.ts) (see [database.md](database.md)) on the critical path; **`marketing_emails_opt_in`** is never set from OAuth—only from Settings. OAuth handlers **`await`** [`runLoginSideEffectsAfterLoginWithLoggedFailure`](../../src/lib/runLoginSideEffectsAfterLogin.server.ts) before returning the redirect ([`runLoginSideEffectsAfterLogin`](../../src/lib/runLoginSideEffectsAfterLogin.server.ts) — OAuth credentials required — runs email backfill then welcome send) so serverless teardown cannot skip work after the response; side-effect failures log via **`logSanitizedApiRouteFailure`** (`Login side effects failed:`) and login still completes. On token reuse, **`recordDiscogsLogin`** failures are logged separately (`Failed to upsert user on token reuse:`). That path backfills **`email`** from Discogs **`GET /users/{username}`** when the column is still empty ([`backfillUserEmailFromDiscogsProfileIfEmpty`](../../src/lib/backfillUserEmailFromDiscogsProfile.server.ts) → [`fetchDiscogsProfileEmailForLogin`](../../src/lib/discogs-profile-email.server.ts); login profile fetch uses **`skipThrottle`**) and sets **`email_verified_at`** (Discogs-sourced address, no self-serve link). User-typed or changed addresses still use **`email_pending`** until confirm. Welcome mail runs when **`email_verified_at`** is set ([`isWelcomeSignupEmailEligibleAccount`](../../src/constants/welcomeSignupEmail.constants.ts)) — after Discogs backfill, verification confirm, or a verified Settings save. **`marketing_emails_opt_in`** stays off until the user opts in in Settings. When login side effects leave **no saved or pending email**, **[`EmailAccountCaptureToast`](../../src/components/EmailAccountCaptureToast/EmailAccountCaptureToast.component.tsx)** (via [`RootToastManager`](../../src/components/ToastManager/ToastManager.component.tsx)) shows a **one-time** bottom-center action toast → **`/settings?section=account`** when [`useToastPresentationGate`](../../src/components/ToastManager/useToastPresentationGate.hook.ts) grants the slot (after higher-priority **`SupportProjectToast`**); dismiss is per-user in **`localStorage`** via [`buildEmailAccountToastDismissedStorageKey`](../../src/constants/storageKeys.ts) ([`emailAccountToastDismissal.ts`](../../src/utils/emailAccountToastDismissal.ts)); closing the toast updates local dismiss state so [`useToastPresentationGate`](../../src/components/ToastManager/useToastPresentationGate.hook.ts) releases the promotional slot in the same session. Promotional hosts use [`useShowToastOnce`](../../src/components/ToastManager/useShowToastOnce.hook.ts) and [`useToastHostReadyAfterMount`](../../src/components/ToastManager/useToastHostReadyAfterMount.hook.ts) ([`PromotionalToastHosts`](../../src/components/ToastManager/PromotionalToastHosts.component.tsx)).
